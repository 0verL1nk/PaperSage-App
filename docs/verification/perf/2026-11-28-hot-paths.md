# 高频主操作性能实测（2026-11-28）

对应 issue：HELE-71。目标：拆开 `/health`、24 KB LaTeX 文件写入、写作提案 apply 三条链路的耗时，
优化后端可控部分，并留下可复现的基准记录（论文第 5 章实测数据来源）。

## 1. 方法与环境

- 生产 API：`https://api-papersage.overlink.top`（Cloudflare → Caddy → Go 单实例，主库为云端 PostgreSQL，对象存储 R2）。
- 探针机：新加坡出口（Cloudflare `loc=SG`），普通宽带；`curl -w` 读取 DNS / TCP / TLS / TTFB。
- 所有数字都是真实生产请求；写入落在临时项目，测后已删除账号与项目。
- 本地基准：`go test -bench`，`httptest` + 内存 SQLite + 内存对象存储，arm64 4 核开发机；
  只覆盖 handler + DB 往返，不含真实网络，因此**以 `queries/op` 作为可移植指标**，ns/op 仅作参考。

同一时段的公网基线（同一探针机）：Cloudflare 边缘 0.35s、Vercel 静态页 0.36s、GitHub API 0.49s。

## 2. 生产实测（优化前）

| 链路 | 样本 | TTFB |
|---|---|---|
| `GET /health`，暖连接 | 6 | 0.69–0.88s |
| `GET /health`，新连接（含 TLS） | 5 | 0.81–2.28s（TLS 0.17–0.33s） |
| 不存在的路由（纯路由器 404） | 3 | 1.36–2.55s |
| `GET /auth/me`（1 次 DB 查询） | 6 | 0.92–5.54s（中位 ~1.15s） |
| `GET /projects`（2 次查询） | 2 | 1.07s / 3.35s |
| `GET /latex-files`（3 次查询） | 3 | 1.13s / 1.37s / 2.38s |
| `PUT` 24 KB（24576 B，内容变化） | 3 | 1.99–2.70s |
| `PUT` 24 KB（内容未变，服务端 md5 短路不写 S3） | 3 | 1.24–2.44s |
| `PUT` 30 B | 3 | 1.07–2.75s |
| `PUT` 75 KB | 5 | 3.32–4.18s |
| `POST /projects`（6 次串行查询 + 1 次 S3 Put） | 1 | 3.53s |
| `POST /latex-files`（75 KB 请求体） | 1 | 7.84s |

## 3. 归因

1. **链路主导**：`/health` 的 handler 只拼 JSON、零 I/O（`server/internal/httpapi/router.go`），
   暖连接仍要 0.69–0.88s，比 Cloudflare 边缘基线高 0.3–0.5s——这段是 Cloudflare→源站往返。
2. **单次 DB 查询在噪声内**：`/auth/me`（1 次查询）、纯路由器 404（0 次查询）与 `/health` 同分布，
   说明本机视角无法把几十毫秒级的查询单独量出来；但串行查询越多，累计越可观。
3. **S3 Put 不是主项**：24 KB 改内容与同内容（不写 S3）无显著差异，差异被链路抖动淹没。
4. **请求体大小显著**：30 B / 24 KB / 75 KB 的 PUT 中位约 2s / 2s / 3.7s，上传耗时随体积上升。
   中文 LaTeX 经 JSON 后 24 KB 字符约 70 KB 字节，是慢上行链路上的主要成本之一。

**结论**：生产端到端由「浏览器 ↔ Cloudflare ↔ 源站」链路与客户端上行主导，后端可控的是串行 DB 往返数。
因此本轮把热路径的串行查询压到最少，并把基准固化成 `queries/op`；进一步压低端到端延迟需要基础设施动作（见 §6）。

## 4. 本轮优化

| 路径 | 优化前 SQL/请求 | 优化后 | 做法 |
|---|---|---|---|
| 读取 `GET /latex-files/{path}` | 3 | **2** | 归属校验与取文件合并为一条 JOIN（`findOwnedFile`） |
| 写入 `PUT /latex-files/{path}` | 4 | **3** | 同上；`UpdateFileRecord` 复用已读记录 |
| 提案 `apply`（含 auth） | 9 | **5** | 提案 + 项目归属 2→1；不再二次读取提案；复用已读稿件记录，去掉 verify + find |
| 提案 `apply`（真实带 tool_call 时） | 10 | **6** | 同上（`closeToolCallOf` 的 1 次 UPDATE 不变） |
| `GET /health` | 0 | 0 | handler 无 I/O，无可优化项 |

所有 404 文案（`Project not found` / `File not found`）与归属校验语义保持不变，由
`TestLatexLookupErrorContract` 与既有越权用例（`TestProposalApplyReject`）覆盖。

### 本地基准（同一台机器，`-benchtime=20x -count=3`）

| 基准 | 优化前（20x × 3） | 优化后（50x × 5） |
|---|---|---|
| `BenchmarkHotPathHealth` | 0.27–0.78 ms/op | 0.32–0.75 ms/op（无变化，符合预期） |
| `BenchmarkHotPathLatexWrite24KB` | 5.43–6.52 ms/op，**4.0 queries/op** | 3.90–4.25 ms/op，**3.0 queries/op** |
| `BenchmarkHotPathProposalApply` | 6.55–7.10 ms/op，**9.0 queries/op** | 3.52–3.89 ms/op，**5.0 queries/op** |

内存 SQLite 下 ns/op 抖动大，且不模拟网络；可移植的结论是查询数。按生产 DB 往返估算的节省（模型，不是实测）：

| 单次 DB 往返 | 24 KB 写入 | 提案 apply |
|---|---|---|
| 50 ms | −50 ms | −200 ms |
| 100 ms | −100 ms | −400 ms |
| 250 ms | −250 ms | −1.0 s |

## 5. 复现

```bash
# 本地基准（输出 ns/op 与 queries/op）
make bench-backend

# 查询预算回归（写 3 条、读 2 条、apply 5 条上限）
cd server && go test ./internal/testutil/ -run 'QueryBudget|LookupErrorContract' -count=1 -v

# 生产探针（需要一个登录 token；不要在命令历史里留真实口令）
BASE=https://api-papersage.overlink.top
curl -sS -o /dev/null -w 'health tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' "$BASE/health"
curl -sS -o /dev/null -w 'me     ttfb=%{time_starttransfer}\n' -H "Authorization: Bearer $TOKEN" "$BASE/api/v1/auth/me"
curl -sS -o /dev/null -X PUT -w 'put    ttfb=%{time_starttransfer} up=%{size_upload}\n' \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  --data-binary @body-24kb.json "$BASE/api/v1/projects/$PROJECT_ID/latex-files/ch2_tech.tex"
```

## 6. 未做与被否的选项

- **不动 `/health` handler**：纯 CPU、零 I/O；冷启动 9.17s 属连接建立与链路，不是代码。
- **不把 S3 Put 改成异步**：写入必须落盘后才返回成功，异步会引入数据丢失窗口。
- **提案 apply 不用进程内 LRU 缓存读稿件**：多实例或外部写入时可能用旧内容通过基准哈希校验，
  再覆盖较新稿件——数据丢失风险，收益（省一次 S3 GET）不抵。
- **请求体压缩（gzip）**：实测请求体大小显著影响写入耗时，但会改前后端契约，本轮不改；
  作为下一步候选（前端压缩 + 服务端解压，需兼容明文请求）。
- **前端保存成功后重新拉取稿件内容**（`useSaveLatexFile` 的 invalidate）：每次保存多一次 24 KB 下行，
  属前端优化项，另行处理。
- **基础设施**：Cloudflare→源站 0.3–0.5s 的固定开销只能靠 Argo/Tunnel、源站与主库/R2 同区域部署等
  方式改善，不在代码仓库范围内。
