# 现代前端工程化最佳实践指南

## 1. 架构选型基准
为了保证高度的风格统一和研发效率，项目核心技术栈收敛为以下组合：
* **核心框架：** React
* **样式引擎：** Tailwind CSS (原子化 CSS)
* **基础组件库：** shadcn/ui (Headless UI + 源码交付)
* **异步状态管理：** TanStack Query (React Query)
* **复杂逻辑抽象：** TanStack Table (表格)、React Hook Form (表单)

## 2. 目录结构规范
合理的目录结构是组件复用的前提。强制实施关注点分离，避免业务逻辑与基础 UI 混杂。

```text
src/
├── assets/        # 静态资源 (图片, 字体等)
├── components/    # 视图组件 (严格按以下层级划分)
│   ├── ui/        # 1. 基础 UI 组件 (由 shadcn/ui 生成，如 Button, Input，全局复用)
│   ├── shared/    # 2. 跨业务线复用组件 (如 通用无数据占位图 EmptyState)
│   └── domain/    # 3. 特定业务组件 (如 UserProfileCard，仅供特定模块使用)
├── hooks/         # 存放全局复用的自定义 Hooks
├── lib/           # 第三方库配置与工具函数 (如 utils.ts, axios 实例)
├── services/      # API 请求层 (按业务模块划分)
├── store/         # 全局客户端状态 (Zustand/Jotai，仅存放主题、用户登录状态等，避免滥用)
├── types/         # 全局 TypeScript 类型定义
└── views/         # 页面级组件 (或 pages/)
```

## 3. 样式与组件开发规约

### 3.1 样式的绝对收敛 (Tailwind CSS)
* **禁止使用行内样式：** 严禁出现 `style={{ color: '#ff0000' }}`。
* **禁止魔术数字：** 所有颜色、间距必须在 `tailwind.config.js` 的 `theme` 中定义 Token（如 `primary`, `spacing-4`），开发时只允许使用预设 class。
* **类名合并规范：** 统一使用 `clsx` 和 `tailwind-merge` (通常封装为 `cn` 工具函数) 来处理动态类名和样式覆盖，防止 Tailwind 类名冲突。

### 3.2 组件库的正确使用 (shadcn/ui 模式)
* **基础组件不引外部包：** 不再引入 `antd` 或 `mui`。所有基础组件（按钮、弹窗、表单输入）通过 shadcn/ui CLI 生成至 `src/components/ui`。
* **统一的定制入口：** 如果团队对按钮的圆角或默认颜色有要求，**直接修改** `src/components/ui/button.tsx` 的源码。所有人调用 `<Button />` 时自动继承团队规范。
* **业务组件封装原则：** 业务组件应该由基础 UI 组件拼装而成。遇到复杂交互（如带验证的复杂表单），使用 React Hook Form 接管逻辑，shadcn/ui 组件负责视图，做到逻辑与视觉的解耦。

## 4. 数据与状态流转规约

### 4.1 服务端状态 (API 请求)
* **封杀 `useEffect` 请求：** 严禁在组件生命周期内手动调用 `fetch` / `axios` 并通过 `useState` 维护 `loading` 和 `data`。
* **全面拥抱 TanStack Query：** * 所有的 GET 请求必须封装为自定义 Hook (如 `useUserListQuery`)，内部使用 `useQuery`。
    * 所有的 POST/PUT/DELETE 请求必须使用 `useMutation`。
    * 利用 Query Keys 进行精确的缓存失效和自动重新获取，保证数据的一致性。

### 4.2 客户端状态
* **局部状态优先：** 尽量使用 `useState` 或 `useReducer` 将状态封闭在组件内部。
* **克制使用全局状态：** 只有确实需要跨多层级级联共享的数据（如暗黑模式状态、当前登录的用户信息），才放入 Zustand 或 Context 中。**不要把服务端取回的数据放进全局 store**。

## 5. 工程纪律与协作规范

### 5.1 避免重复造轮子的三大原则
1.  **先搜后写：** 开发新组件前，必须先在 `components/shared` 和 `components/ui` 中检索。
2.  **三次法则 (Rule of Three)：** 一段 UI 代码在项目中出现第一次时，先写死；出现第二次时，复制粘贴；出现**第三次**时，必须立刻将其重构并抽离至 `shared` 或 `ui` 目录。
3.  **单向依赖：** `ui` 组件不能依赖 `shared` 组件，`shared` 组件不能依赖 `domain` 组件。下层组件绝对不能包含上层业务逻辑。

### 5.2 自动化防线
* **Linter & Formatter：** 强制开启 ESLint 和 Prettier。配置 ESLint 插件检查 Hook 依赖和 Tailwind 排序 (`eslint-plugin-tailwindcss`)。
* **Git Hooks：** 配置 `husky` + `lint-staged`，在 `git commit` 前自动格式化代码并进行类型检查，不符合规范的代码禁止提交。

---

在这套架构下，基础组件交给了 shadcn，样式交给了 Tailwind，数据流交给了 TanStack，开发者只需要专注拼接业务逻辑即可。

针对这套规范，在实际落地时，你通常倾向于在这个技术栈基础上搭配哪种路由方案（比如 SPA 模式的 React Router / TanStack Router，还是直接上 Next.js 这样的全栈框架）？
