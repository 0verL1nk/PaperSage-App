# 毕设总体逻辑与决策台账

更新：2026-09-19。状态：**已吸收第一轮 Grill 决策与联网调研；不是已实现功能清单，也不替代后续 OpenSpec 与验收记录。**

本文件把“基于大模型的科研论文写作 AI 辅助系统设计与实现”的产品主线、工程边界和待决问题放在同一处。目的不是把所有设想提前承诺，而是让开题报告、答辩、需求、架构和后续实现讲同一个可信的故事。

## 1. 一句话定位

本系统不是替学生自动生成论文的聊天机器人，而是一个**面向本科生和研究生等科研新手、以项目上下文为中心、以统一项目知识空间和用户确认的研究蓝图为依据、在论文全过程提供可追溯建议的 Web 工作台**。

“全流程”表示覆盖“弄清研究任务—组织资料—分章节写作—多维检查修改”的完整过程并保留项目上下文；不表示系统自动完成论文，更不表示它替代导师、保证学术结论或自动通过规范审查。

与通用对话式工具相比，系统应形成四个可答辩的差异：

1. **项目上下文**：理解一个持续存在的研究项目，而不是只处理一轮临时对话；
2. **有据可查**：建议尽量能回到任务书、校级规范、用户资料或可核验的外部来源；
3. **阶段化辅助**：准备、撰写、检查阶段有不同目标、上下文和输出形式；
4. **用户最终控制**：AI 提出建议、理由与候选修改，用户决定采纳、编辑、忽略或要求复查，且对论文承担学术责任。

## 2. 应贯穿始终的一条主线

三阶段是用户旅程，不是三个互不相干的子系统。系统的核心闭环如下：

```text
用户研究问题、任务书、LaTeX 模板/规范、参考文献、代码与实验材料
                                  ↓
统一项目知识空间（所有资料可存、可读、可检索、可追溯）
                  ↕ 研究任务澄清 / Agentic Search 持续增量入库
用户确认的研究蓝图、阶段状态与当前稿件
                                  ↓
按阶段组织项目上下文与任务
          ↓
规则检查 / 检索增强分析 / 受控 AI 任务
          ↓
带位置、理由、证据和不确定性的建议
          ↓
用户采纳、编辑、忽略或补充材料
          ↓
稿件、项目状态、资料库和审阅记录持续演化
```

这意味着“资料库”“研究蓝图”“稿件”和“建议记录”是跨阶段长期存在的对象。资料库不是准备阶段结束后冻结的附件集合；AI 生成的摘要、Wiki 或关系只能是可回溯的派生内容，不能取代原始资料。

## 3. 责任边界与非目标

### 3.1 人与 AI 的边界

| 系统可以做 | 系统不应宣称或静默执行 |
|---|---|
| 根据用户明确的任务，组织资料、解释规范、发现可能的逻辑跳跃、证据不足和表达问题 | 判断某个学术结论一定正确，或保证引用、规范、查重结果一定无误 |
| 给出提纲、局部表述、修改候选与完整理由 | 自动覆盖正文、替用户决定研究方案或虚构实验数据 |
| 在来源充分时提示“该论断可能由哪些资料支持” | 没有依据时伪造文献、页码、实验结果或事实 |
| 模拟预设量表下的多维审阅 | 宣称可替代导师指导、给出权威评分或代替学术责任 |

任何涉及稿件、研究蓝图、长期项目记忆或公共规范的修改，均应形成可查看的候选变更；服务端只在用户确认后写入。

### 3.2 明确非目标

本科毕设不把以下内容作为必须验收承诺：基础大模型训练、自动投稿、查重/AI 生成检测、自动下载或传播受版权限制全文、复杂 OCR、多校多学科完整规范、实时多人协作、任意格式双向 Word 编辑、任意用户代码执行和拆分为大量微服务。

## 4. 三阶段：输入、任务与可见产物

| 阶段 | 用户在解决什么问题 | 系统的受控任务 | 关键产物 |
|---|---|---|---|
| 写作准备 | “我的课题究竟研究什么、已有何种依据、还缺什么？” | 研究任务澄清、资料入库、规范选择、资料检索、计划与大纲建议 | 已确认的研究蓝图、资料来源台账、章节计划/大纲、待补项 |
| 内容撰写 | “如何在自己的研究方向和规范约束下把这一章节写清楚？” | 按需的提纲、段落逻辑、表达、论断—证据、引用缺口和规范建议 | 稿件版本、批注、候选修改、证据引用、采纳/忽略/编辑记录 |
| 检查完善 | “全文有哪些优先级不同的问题，应如何逐项完善？” | 规则检查与多维审阅汇总 | 带定位、严重程度、理由、依据和复查状态的问题清单 |

阶段可以反复往返。缺材料时，系统的正确结果是列出待补材料或待核查事项，而不是补造内容。

## 5. 一个统一项目知识空间，而不是多套资料库

用户看到的应是一套**项目知识空间**：参考文献、网页快照、代码仓库、实验数据、个人研究设想、LaTeX 模板、规范、当前稿件、Agentic Search 结果和 AI 生成的 Wiki 均可进入其中、被阅读和被检索。它不是“文献库 + 代码库 + Agent 记忆”三个彼此隔离的产品。

内部仍须保存材料类型、来源、版本和可信状态。这不是把知识拆开，而是避免 AI 把“论文原文”“自己生成的摘要”“用户尚未验证的想法”误当成同等级事实。概念上可统一为 `KnowledgeItem`；真实表结构和接口以后续设计为准。

| `KnowledgeItem` 需要表达什么 | 典型内容与约束 |
|---|---|
| `kind` 与 `origin` | 原始论文、网页快照、代码仓库、数据集、研究设想、LaTeX 模板、规范、稿件、AI 摘要等；用户上传/录入、Agent 搜索或系统生成 |
| `version` 与 `provenance` | 文件哈希、网页抓取时间、仓库 commit、稿件版本；由谁、何时、基于哪个任务产生 |
| `status` 与 `permission` | 候选、已确认、可作为正式证据、已过期、解析失败；是否可进入本次 Agent 上下文或正式引用 |
| `locator` 与 `EvidenceRef` | PDF 页码/段落、网页片段、代码仓库/commit/path/symbol/行号、数据表/字段或实验记录位置 |
| 派生内容和关系 | 文本块、摘要、LLM Wiki、标签、实体、主张和关系边；必须回链原始资产和版本，可重建 |

项目与权限仍是外层边界：一切知识项、检索和模型上下文按项目隔离。研究蓝图、稿件与审阅记录是知识空间中具有更严格确认规则的特殊对象，而不是无边界的聊天记忆。

### 5.1 “Grill me”的正式产品含义

系统中的 Grill 不应只是把对话无限保存为 memory，而应命名为**研究任务澄清向导**：通过追问形成一份可编辑、可版本化、待用户确认的 `ProjectBrief`。它是项目知识空间中“当前研究事实和约束”的受控入口。

首版建议至少询问并记录：

- 研究主题、背景和核心研究问题；
- 研究目标、预期成果和不应超出的范围；
- 研究对象、数据/代码/实验条件和已有材料；
- 拟采用的方法、系统功能或技术路线；
- 论文的关键章节、时间节点和学校/导师约束；
- 已知事实、假设与尚未证实的事项。

后续发现用户的研究方向已改变时，系统应提示“是否更新研究蓝图”，由用户确认，而不是静默篡改长期上下文。

## 6. 统一知识空间中的资料生命周期、Agentic Search 与关系增强检索

### 6.1 统一入库与资料生命周期

```text
用户上传/录入 + Agentic Search + 项目策略允许的网页检索 + 代码/实验材料
                                      ↓
统一 `KnowledgeItem`：保存原件或快照、来源、哈希、版本、权限与状态
                                      ↓
按类型适配解析：文本分块 / 网页快照 / 代码符号 / 数据字段与实验记录
                                      ↓
关键词 + 向量混合检索，必要时关系扩展检索
                                      ↓
摘要、LLM Wiki、标签、关系建议（均为可回溯的派生知识）
                                      ↓
为研究、计划、写作建议和全文审阅按需提供证据
```

新资料不必被“分配到另一个库”。Agentic Search 搜到的网页、Agent 形成的调研笔记和用户上传的资料都可自动创建知识项并被读取；其中前两类应标出来源和 `candidate/derived` 状态，只有满足项目规则的原始资料/快照才能作为正式证据。这样既满足“统一地存、统一地读”，又不会让 AI 摘要伪装成论文引用。

首版资料格式仍应主动收敛。PDF、DOCX、Markdown/TXT、LaTeX、网页快照、代码仓库快照和基础实验记录可以处于同一知识空间，但每种格式的“可保存”“可全文检索”“可准确定位”“可理解表格/图片/语义结构”等能力必须分别声明，不能把文件能上传说成 AI 已完全理解它。

### 6.2 LLM Wiki、Hybrid RAG 与 Graph RAG 的分工

- **LLM Wiki**：面向用户阅读和后续任务的派生笔记/结构化整理，不是原始证据的替身；应显示原文来源和版本。
- **Hybrid RAG**：承担默认的局部证据召回——例如“这段话可由哪篇文献的哪一页支持”“某篇资料如何定义该方法”。它应保存检索方法、分块身份、索引代次和定位信息。检索结果存在，不等于它支持模型给出的任一论断。
- **Graph RAG/关系检索**：承担两个 Hybrid RAG 不擅长的问题。第一是全局归纳，例如“全部已入库资料有哪些研究路线、争议、常用方法、数据集和评价指标，它们与我的研究问题有何关系”；第二是多跳证据追溯，例如“第 3 章这项方法分别由哪篇文献、哪个代码模块、哪组实验指标支撑，哪些部分仍缺证据”。Microsoft GraphRAG 将前者称为全局搜索，将后者的局部实体关系与原始文本共同用于局部搜索；这正说明图不是原文检索的替代品，而是关系增强层。[Global Search](https://microsoft.github.io/graphrag/query/global_search/) / [Local Search](https://microsoft.github.io/graphrag/query/local_search/)

关系层至少要能表达 `研究问题—方法—主张—论文段落—原始资料—代码模块—数据集/实验指标`，并保存 `supports / contradicts / defines / uses / evaluates / implements / cites` 等关系的来源、版本、置信度和人工确认状态。完整复刻 Microsoft GraphRAG 的实体/关系抽取、社区发现和多层摘要成本很高；本课题更适合先实现轻量“写作证据关系图”，再以真实全局问题和对比测试决定是否升级为完整 Graph RAG。

### 6.3 CodeGraph 是代码实现证据层，不是第二个资料库

- 代码材料的首要写作价值是帮助用户说明“系统如何实现”“某个实验/模块对应什么证据”。CodeGraph 的明确增量不是“让 Agent 更会读代码”，而是让论文中的实现表述能追溯到 `repo@commit/path/symbol/line` 和必要的依赖链。例如：“从登录到进入写作工作台经过哪些路由、服务和前端页面？”“论文写到异步资料解析时，真实任务入口、解析服务、索引写入和测试依据在哪里？”
- 普通文件级 RAG 能找出相似代码片段，却容易遗漏跨层调用和依赖关系；代码图可把 `路由 → Handler → Service → Model/存储 → 前端页面` 或 `论文论断 → 模块 → 接口 → 测试` 组织为可回查链路。RepoGraph 等仓库级研究的价值正是以结构化关系帮助模型在仓库中导航，而非只按片段相似度检索。[RepoGraph（ICLR 2025）](https://openreview.net/forum?id=dw9VUsSHGB) / [Aider Repository Map](https://aider.chat/docs/repomap.html)
- 首版可从仓库快照、目录、README、关键模块、文件/符号定位和导入关系开始；再针对 Go/Gin 与 TypeScript/React 做有限的路由、接口和调用链解析。完整跨语言调用图、运行时行为推断、任意代码执行和“自动判定架构正确性”不应承诺。
- 上传代码默认只做解析与索引，不执行代码；应忽略 `.env`、密钥、依赖目录和二进制大文件。

### 6.4 Agentic Search 是统一知识空间的检索与增量入口

Agentic Search 不是另一个“搜索资料库”，而是 Agent 围绕当前研究问题、论文阶段和知识空间缺口进行的受控检索编排：先提出检索计划，再选择本地混合检索、关系扩展、代码/数据读取或项目策略允许的互联网检索，最后把结果和过程留痕。

外部检索结果应保存 URL、访问时间、来源类型、网页快照、筛选理由和任务记录。Agent 将结合主题相关性、来源质量、证据可用性、增量价值、时效、重复性及版权/隐私硬规则，自主决定接受、仅保存元数据、延后、拒绝或隔离；具体协议见[《Agent 技能与统一知识空间治理协议》](14-agent-skills-and-knowledge-governance.md)。学校订阅或版权受限全文不应被系统自动绕过、抓取、下载或向模型扩散。涉及事实、方法、实验结论、相关工作和参考文献的建议必须回传证据；局部润色等不涉及事实的任务不必为了“看起来 Agentic”强行联网。

### 6.5 “Dream”的收敛定义

“Agent 不定时 dream”在工程和论文中统一称为**异步资料整理与增量索引任务**。它可更新分块、索引、摘要候选、标签或关系建议，且应显示进度、失败、重试和来源版本；它不得静默删除原资料、改写稿件、把未经确认的结论写入研究蓝图，或无限制调用外部模型。

## 7. Agent 不是固定场景自动化：开放规划与任务契约

“Agentic”应体现在复杂任务的受控编排，而不是每次输入都允许模型无限循环和联网。下表是常见任务原型，不是 Agent 能力的封闭菜单：运行时 Planner 可以依据稿件、知识、规范和事件变化组合多项 Skill。每次 `WritingRun` 至少固定：

```text
任务类型 + 项目/权限 + 稿件或选区版本 + 研究蓝图版本
+ 适用规范版本 + 资料/索引版本 + 提示策略版本
+ 可调用工具白名单 + 步数/时间/token 预算
```

建议按任务决定是否检索、是否调用工具：

| 任务 | 必要上下文和工具 | 输出边界 |
|---|---|---|
| 语句精简、语法或风格调整 | 当前选区及有限上下文；默认不检索 | 不添加新的事实、数据或引用；有歧义时提问 |
| 计划与大纲 | 研究蓝图、规范、资料状态；按需检索 | 输出结构理由、待补项和候选方案，要求用户确认 |
| 论断—证据/引用检查 | 当前段落、项目原始资料、证据定位 | 无充分依据时只提示核查或补充资料，不能伪造引用 |
| 代码或实验说明 | 用户授权的代码/数据材料与项目蓝图 | 指出可回查实现证据；不执行用户代码、不捏造实验结果 |
| 研究现状、资料全局梳理或跨材料追溯 | 先混合检索，再按项目策略做关系扩展或联网检索 | 返回检索计划、来源、关系链和不确定性；新资料留痕入库 |
| 全文多维审阅 | 全文/章节、目录、研究蓝图、规范和必要证据 | 返回结构化问题清单，而不是不透明的“论文分数” |

所有模型工具均由服务端控制白名单、超时、调用次数、预算、权限和错误状态；上传资料中的文字也只能被视为资料，不得改变这些工具权限。

## 8. 撰写过程中的事件、版本与用户确认

用户持续编辑时，系统最容易犯的错误是让一个耗时 Agent 把旧稿建议应用到新稿。因此建议把事件模型作为核心设计，不把它仅当作前端交互细节。

```text
用户编辑 → 生成稿件版本/编辑事件
         → 对“项目 + 章节/选区 + 任务类型”做防抖合并
         → Agent 以版本快照执行
         → 返回前再次校验版本
         → 匹配：展示候选建议；不匹配：标为 stale（过期），不得自动写回
```

建议与修改至少有以下状态：

```text
任务：queued → running → completed / failed / cancelled / stale
批注：open → resolved / rejected / stale
候选修改：pending → applied / rejected / stale / failed
```

写作阶段的主交互应是类似导师审阅的**批注**，而不是频繁弹出的泛化建议。局部问题附着在基准快照的原文选区；全文结构、章节安排、引用覆盖等没有唯一选区的问题，以文档级批注在侧栏呈现。每条批注至少包含“问题是什么—为什么提示—稿件位置—规范或原始资料依据—适用稿件版本—不确定性/局限”；需要替换文字时，才附带可预览的候选修改。

用户可接受候选修改、手工修改后标记已处理、拒绝/忽略、继续追问或要求复查。候选修改绝不因批注生成而自动写入；服务端应审计处理决定，并校验项目归属、基础版本和幂等性。若新快照改变了批注所锚定的文本，系统应将其标为 `stale` 或要求重新定位，不能把旧批注的修改直接套到新稿。

所有触发方式均可使用：显式请求、保存后防抖、章节完成、资料入库、编译/规范异常和稿件 snapshot 的语义变化都可以产生分析机会。是否真正执行由 Agent 根据结构、研究语义、证据、表达和 LaTeX 工程差分，以及阶段、预算、未处理问题与冷却时间动态决定；具体事件模型见[《事件驱动写作辅助与多维论文审阅模型》](15-event-driven-writing-and-review-model.md)。

### 8.1 LaTeX 是唯一的稿件主格式，模板是项目知识项

第一版不做 Word 编辑、导入导出或双向同步。每个写作项目以 LaTeX 工程为唯一规范稿件：用户可上传一个受支持的模板工程，或从系统内置模板中选择；模板的 `.tex`、`.bib`、图表资源、编译配置和适用规范都作为项目知识空间中的可版本化项目保存。

AI 对正文、参考文献或 LaTeX 结构的任何建议都应先以批注呈现；需要替换时，批注包含差异候选，用户确认后才写入工程。模板上传、编译和资源访问还需设置安全边界，不能让模板中的命令获得任意宿主机执行权限。

## 9. 最终检查：多维审阅流水线，而非概念堆叠

第三阶段的对外定位建议是“基于预设量表的多维审阅与汇总”，不是无约束的“导师 Agent 集群”。审阅不应仅限于格式、逻辑、引用和表达，而应按学位层次、学科、论文类型、研究方法、模板/规范和已有材料形成 `ReviewProfile`，从维度库选择选题/贡献、相关工作、研究问题、方法、系统实现、数据/材料、实验设计、结果图表、局限、可复现性、伦理/学术诚信、结构表达与 LaTeX 交付等检查项。

本科系统类论文通常更看重专业能力、系统实现、实验/测试和基本学术规范；研究生论文还要更严格检查研究贡献、创新边界、方法/数据严谨性和研究过程。并非所有维度都适用于每篇论文，系统必须允许标注“不适用”，而不是制造假问题。各审阅 Skill 必须读取同一份稿件快照、研究蓝图和证据包；汇总器负责去重、处理冲突、按严重程度排序。每条结果需要有定位、问题类型、理由、依据、建议、优先级及复查状态。细化模型和调研依据见[《事件驱动写作辅助与多维论文审阅模型》](15-event-driven-writing-and-review-model.md)。

## 10. 适合本毕设的范围分层

| 层级 | 应包含的能力 |
|---|---|
| **MVP / 必须完成** | 面向本科生与研究生的同一三阶段主流程，以场景配置、规范和 LaTeX 模板适配差异，而不建设两套系统；项目级统一知识空间，支持原件/快照、版本、混合检索和来源回查；研究任务澄清并确认研究蓝图；默认读取项目知识的受控 Agentic Search，按主题和资料质量自主作出可审计的入库决定；事件驱动的章节级智能批注、候选差异与用户确认、版本过期保护；LaTeX 模板上传/选择；本地目录、ZIP、Git 地址三入口的代码仓库快照（不执行代码）；实验资料保存和证据核查；基于 `ReviewProfile` 的规则、证据和推理审阅；分层测试与可演示主路径 |
| **P1 / 核心完成后** | 轻量“主张—证据—章节—资料”关系视图和关系扩展检索；代码仓库目录/符号/接口级实现证据映射；用户触发的资料整理；更丰富的审阅角色、模板和规范包 |
| **P2 / 时间与证据充足后** | 完整 Graph RAG 的全局主题/社区总结与多跳图检索；面向既定技术栈的 CodeGraph 调用链；多 Agent 协商；定时异步整理；复杂 OCR、多模态材料理解和深度联网研究；用户确认的受控 SSH 实验执行连接器 |

建议答辩演示先锁定一条不超过八步的黄金路径：

```text
创建论文项目，选择/上传 LaTeX 模板并填写研究问题
→ 上传任务书、规范、参考文献、已有代码/实验材料
→ 研究任务澄清向导生成并确认研究蓝图
→ Agentic Search 将补充调研结果作为可回查知识项入库
→ 在某章节主动发起“论证与引用检查”
→ 系统展示可回查批注
→ 用户采纳/编辑/忽略
→ 发起多维全文检查
→ 获得可跟踪的待修改清单
```

## 11. 验收逻辑与真实主张

本课题可验证的是系统能力和使用过程，不应在没有对照实验的情况下声称“显著提升论文质量”或“减少导师负担”。建议至少组织：

- 功能测试：两场景（若实现）× 三阶段，资料、规范、建议、确认、审阅等主流程；
- 来源与安全测试：来源回查、版本失效、无依据时不伪造引用、权限隔离、私有资料最小化外发；
- 异步与异常测试：取消、模型失败、检索降级、编辑后过期建议、重试与恢复；
- 性能测试：典型文件解析、检索、建议与全文检查的响应时间/成功率；
- 可用性验证：明确样本和量表；若只做开发者自测或小样本体验，应如实描述，不泛化为教学效果结论。
