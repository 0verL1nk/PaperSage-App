# 结合学术写作研究的整体设计评审

评审日期：2026-10-01；采纳记录更新：2026-10-04。状态：**用户已要求落实评审建议，设计基线已同步，功能仍待实施。**

第1—10节保留原始评审及建议，文中“当前缺口”“文档冲突”反映评审时的状态。最新规则以11—15号文档为准；本轮的具体采纳与同步记录见第11节。

## 1. 评审依据与结论

本次阅读 [项目总览](../PROJECT.md)、[调研驱动方案](12-ai-writing-design.md)、[总体逻辑与决策台账](13-thesis-product-model.md)、[知识空间治理](14-agent-skills-and-knowledge-governance.md)、[事件与审阅模型](15-event-driven-writing-and-review-model.md)、[开发路线图](11-roadmap.md)、正式开题报告，以及进行中的 AI 模块设计和规格。评审对象是设计文档，没有据此判断当前业务代码完成程度。

当前的统一知识空间、研究蓝图、可回查证据、人工确认、开放式 Agent 和多维审阅方向值得保留。主要优化空间在于：**把材料怎样转化为论证、章节怎样相互支撑、系统怎样帮助新手推进下一步写清楚，并统一已有规则。**

建议将总体主线具体化为：

```text
研究任务澄清
  → 整理已有材料并诊断缺口
  → 比较研究路线、形成有依据的章节计划
  → 围绕章节目标组织论断和材料
  → 生成写作建议或局部候选
  → 用户修改与确认
  → 检查局部问题及跨章节一致性
  → 回到需要调整的材料、计划或正文
```

这条主线贯穿原有准备、撰写、检查三个阶段。阶段允许往返；用户可以直接进入任一任务，系统根据已有材料补充必要步骤，不设置必须完成全部前置任务才能编辑的门槛。

## 2. 从文献中借鉴什么

| 研究 | 已核对的方法要点 | 本项目的设计推导 |
|---|---|---|
| [AutoSurvey，NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/d07a9fc7da2e2ec0574c38d5f504d105-Abstract-Conference.html) | 检索与大纲生成、分节撰写、整合修订、评价 | 将章节计划和整合检查作为明确的中间产物 |
| [ChatCite，COLING 2025](https://aclanthology.org/2025.coling-main.244/) | 提取文献关键要素，通过增量比较与反思修订生成综述 | 为相关工作任务加入可回查的比较材料，明确比较轴 |
| [InteractiveSurvey，2025 年预印本](https://arxiv.org/abs/2504.08762) | 用户可调整文献分类、大纲和生成内容 | 让用户修改写作依据和组织结构，而非只能对最终文本接受或拒绝 |
| [SurveyForge，ACL 2025](https://aclanthology.org/2025.acl-long.609/) | 参考人工综述结构生成大纲，检索并完善正文，分别评价文献、大纲和内容 | 对组织过程和最终输出分别检查，明确范式适用理由 |

上述是论文方法与本项目工程推导的对应关系。它们主要研究综述写作，不能直接证明本科毕设全流程辅助有效；也不意味着本项目应复刻各自的全部管线或数据库。

## 3. 首要补充：可编辑的资料比较与论证计划

### 3.1 当前文档的缺口

13 号文档定义了研究蓝图、知识项、大纲、稿件与建议；14 号文档定义了证据绑定与参考范式；15 号文档提出检查“只罗列不比较”。但还未具体定义：多篇资料如何组成比较，比较结果如何影响章节结构，章节怎样从目标推进到结论。

### 3.2 建议增加的中间产物

这些产物都属于统一项目知识空间中的可版本化派生对象，可以复用通用存储，不要求立刻拆成独立数据库表或新的子系统。

| 产物 | 至少表达什么 | 用户怎样使用 |
|---|---|---|
| 文献阅读记录 | 问题、方法、研究对象、评价条件、主要结果、适用限制；每项对应原文证据或“未报告” | 核对模型提取是否准确，补充阅读判断 |
| 文献比较 | 本次问题、比较轴、所选文献、共性、差异、冲突、材料缺口及证据 | 调整分类、比较轴和纳入资料，避免逐篇罗列 |
| 章节计划 | 章节职责、要回答的问题、拟表达的论断、现有依据、缺项和与其他章节的关系 | 在写作前或写作中修改论证顺序 |
| 章节摘要与术语记录 | 当前版本实际写了什么、核心结论、术语定义和引用到的材料 | 为后续章节和全文一致性检查提供导航 |

不同研究条件下的结果不能直接合并比较；原文未提供的信息应保留缺项。比较结论、聚类和研究缺口均是候选分析，不自动升级为用户已确认的研究事实。

“文献比较”是内部与按需查看的辅助视图，可以用列表、分组卡片或矩阵呈现；无需让用户先手工填写完整表格再开始写作。

### 3.3 相关工作任务的建议流程

```text
读取本项目研究问题与当前章节
  → 确定比较轴，如任务、方法、输入材料、评价与适用范围
  → 对选定文献提取带来源的要素
  → 形成分组及比较候选，用户可调整
  → 形成章节计划与待补项
  → 生成围绕比较关系的局部写作候选
  → 核查引用与原文支持关系
  → 用户采用、编辑或返回调整比较
```

这不是所有任务的固定入口。润色无需文献比较，实验讨论更需要用户结果与实验条件，系统设计章节更需要目标、约束、模块与实现材料。开放式 Planner 按任务组合这些步骤。

## 4. 章节协同：明确章节之间的逻辑依赖

### 4.1 大纲需要表达章节职责

目前大纲主要用于目录和阶段组织。建议补充以下关系：

- 引言提出的研究问题，在哪个方法或设计章节得到回答；
- 设计目标，在哪些功能、实现和测试中得到检验；
- 结果支持哪些结论，哪些仍未覆盖；
- 摘要与结论，是否超出了正文中的实际证据。

关系绑定项目对象和可回查位置。确定性关系可由用户明确建立，模型提取的关系保留候选状态；无需先建设完整知识图谱才能提供这些关联。

### 4.2 章节任务的上下文

建议每次章节任务使用：研究蓝图的相关字段、该章计划、当前选区、相关原始材料、相邻或依赖章节的摘要、适用规范。摘要用于导航；涉及事实核查或矛盾时，应回读具体章节和原文，不能只凭摘要认定问题。

章节变化后，更新该章摘要并将影响传播到依赖它的计划、批注和检查任务。整合检查重点识别重复论述、术语变化、目标遗漏、结果与结论不一致；不需要每次把全文重新生成一遍。

## 5. 面向新手的交互：建议要能推进下一步

既有批注、来源回查和候选修改值得保留。建议进一步定义三类交付：

1. **如何组织**：说明该章要回答什么问题、建议的论证顺序和相应材料。
2. **为何修改**：给出问题位置、原因、必要依据和局部候选。
3. **还需补什么**：列出缺失材料与下一步，如补检索某类研究、补实验环境、缩小尚无证据的结论。

例如用户说“帮我写研究现状”，系统可以先给出按方法分类的候选组织和证据缺项；用户已有成熟稿件时则直接进行比较、引用和结构检查，不强迫其重新走准备向导。

每次任务默认优先展示少量最有价值的下一步，允许展开全部分析。资料比较、大纲和计划可随时修改；模型解释应简短并能回查依据，不展示冗长内部推理。

LaTeX 继续作为已确认的唯一稿件格式。可通过模板、正文编辑定位和编译错误解释降低使用门槛，不新增 Word 双向编辑作为本次优化的前提。

## 6. 统一资料自动入库与确认边界

### 6.1 文档中的冲突

13 号文档 3.1 将长期项目记忆修改统一列入用户确认；14 号文档 1、4、6 则明确 Agent 自主资料准入，普通入库不需逐条批准。若将派生笔记全部归入长期记忆，两条规定会冲突。

### 6.2 建议按对象的作用统一

| 对象或操作 | 建议规则 |
|---|---|
| 用户上传原件、Agent 合规搜索结果、元数据、索引 | 按既定策略自动保存、版本化与留痕；保留用户纠偏权 |
| AI 摘要、比较、范式、标签和关系候选 | 可自动生成和保存，清楚标记为派生分析；不自动变成已确认事实 |
| 研究蓝图中的正式目标、方法和已确认事实 | 形成候选更新，由用户确认 |
| 稿件、正式引用与公共规范的变更 | 沿用相应授权与确认规则；普通资料入库不能触发稿件写回 |

资料状态还应拆分为处理进度与证据核查状态。“解析和定位完成”表示可以回查，不表示已验证某条论断；`evidence_ready` 若保留名称，应在界面明确这一含义。特定论断的支持关系单独记录为支持、反驳、条件不同、未说明或无法判断，并附证据和核查方式。

## 7. 按实际依赖判断过期，减少重复任务

### 7.1 现有规则的问题

15 号文档 2.4 规定稿件、研究蓝图、知识索引和规范版本任一不一致即 `stale`。这是保守规则，但与持续编辑和自动增量入库组合时，容易使仍有参考价值的建议反复失效。

例如用户只在结果章修正标点，相关工作章的文献比较不应因此全部重做；新加入一篇无关资料，也不应使所有局部润色过期。

### 7.2 建议的依赖记录

每次任务记录实际读取的稿件范围、章节计划、研究蓝图字段、原始材料版本、规范条目和提示配置。根据这些依赖区分：

- **仍适用**：无相关依赖变化，保留参考价值；
- **待复查**：相关材料或研究约束有变化，需要重新核查；
- **已过期**：锚定原文或关键论证依据改变，旧候选不能继续应用。

全局审阅可依赖整个稿件快照；局部任务只声明其实际所需范围。无法确定影响范围时采用保守失效。

候选修改的写回仍严格校验当前版本。即使旧分析仍有参考价值，只要基础稿件变了，就不能直接套用旧差异；需形成当前版本上的新候选并重新确认。来源撤权或删除应立即阻止后续使用，不因依赖范围优化而继续可用。

## 8. 让复杂机制服务于明确场景

现有 Graph RAG、CodeGraph、范式学习和多维审阅已有适用方向。建议进一步按场景定义最小可解释输出，并与后续扩展明确对应：

| 需要解决的具体问题 | 可先采用的设计 | 更复杂方法的启用依据 |
|---|---|---|
| 多篇文献有哪些研究路线 | 带来源的阅读记录、比较与分组 | 普通组织方式遗漏重要关联时，试验关系扩展 |
| 某章节论断有哪些依据 | 论断与原文、代码、结果记录之间的显式链接 | 明确需要跨材料多跳追溯时增加图查询 |
| 大纲是否合理 | 章节职责、项目目标、用户可调整的参考范式 | 确认范式检索比通用结构建议更适合该任务 |
| 哪些问题值得主动提示 | 编辑范围、引用、章节与规范事件先确定影响面，按需进行模型分析 | 经测试再调语义分析频率、合并窗口与预算 |
| 全文审阅如何执行 | 依据 ReviewProfile 组合规则与分析任务，使用统一证据及输出格式 | 实验显示有收益时再引入额外审阅协商 |

开放式 Agent 继续按意图组合 Skill；运行、存储、依赖检查和应用修改由确定性的服务协调。模型负责内容规划与分析，不自行决定版本事务是否成功。

## 9. 评价设计与文档口径统一

正式报告 3.4 计划约 30 个固定写作任务，另设开发任务，开展通用提示与场景提示对照。12 号文档 9.2 写的是 20 个开发任务、40 个测试任务，并列出三种生成设置。不能继续将二者称为同一实验。

建议统一为以下层次：

1. **系统验收**：两场景、三阶段、资料、计划、中间产物编辑、批注、版本、编译与异常流程；保持功能、性能和开发者走查的现有约定。
2. **提示评价**：以正式报告约 30 个固定任务为基线，冻结开发与评价数据；同模型、参数、材料、资料片段比较通用提示与场景提示。若给模型提供比较记录或章节计划，两组应使用同样产物，避免混淆提示优化与额外上下文的作用。
3. **流程探索评价**：从固定任务中另外选择资料综合和章节组织任务，比较直接生成与“提取—组织—生成—检查”的表现。两组保持模型与原始材料一致，记录组织质量、错误、用量和完整耗时；流程输入变化必须明确说明，结果单列。

评价可增加可操作指标：文献要素与原文一致性、比较是否成立、章节职责覆盖、跨章节矛盾定位、引用是否支持论断、缺材料时是否正确提示。不是只评价文本流畅度。

不把流程探索全部纳入同一次提示实验；也不因为论文中有多人研究就扩大本项目既定的开发者自评范围。测试数量、是否做流程探索及评分说明需在实施前明确冻结，未经实施不能报告收益。

## 10. 一个贯穿全流程的示例

用户拟写计算机系统类毕业论文，已有项目说明、规范、若干参考论文、代码快照和测试记录。

1. 澄清研究问题、目标和已有成果，形成用户可修改的蓝图。
2. 以任务、方法与评价方式组织参考文献，发现缺少某类可比研究；Agent 按既定准入策略补充资料并留痕。
3. 生成相关工作章计划：比较哪些路线、怎样说明与本项目的关系、哪些判断缺证据。
4. 用户调整分类或计划，系统基于对应证据生成局部候选，经用户编辑确认后进入稿件。
5. 系统设计章读取设计目标、章节计划和实现材料，帮助解释设计选择及数据流。
6. 测试章读取用户记录，检查环境、指标、基线和结果说明；缺数据时提出待补项。
7. 全文检查将目标、实现、测试和结论对应起来，指出未验证目标、无依据结论或重复内容。
8. 用户回到相应章节处理问题，系统只复查受影响部分并保留过程记录。

这个示例能够同时说明系统业务、AI 作用、可见产物与验证方式，也适合转化为后续演示案例。
