# 调研驱动的 AI 写作实现方案

更新：2026-10-04。状态：**后续实施基线，不是已实现或已通过测试的声明**。已纳入文献比较、章节论证计划与跨章节检查；本轮仅调整文档，不修改业务代码、数据库或既有 OpenSpec 完成状态。

## 1. 定位与范围

正式课题为“基于大模型的科研论文写作AI辅助系统设计与实现”，面向中国大陆本科生及科研入门者。以课题要求的两类场景、三阶段流程、四个业务模块为主线，研究重点是系统设计、提示优化和测试，不是训练基础模型或提出新的检索算法。

保留现有 React/TypeScript 前端和 Go/Gin 后端，沿用现有编辑、存储与编译能力。前后端分离指交互与服务职责分离，不要求为了答辩拆成许多微服务。暂不新增 Python 解析服务、Elasticsearch、独立向量数据库等必需依赖；部署数据库及向量扩展的兼容性由实际迁移和集成测试确定，不因存在适配分支就宣称全部支持。

必做：用户管理、分场景写作工作台、全流程 AI 辅助、学术规范资源库；持久化、来源核查、用户确认、部署演示和三类测试。复杂 OCR、跨项目知识图谱、实时多人协作、自动投稿、Word 双向编辑、查重/AI 检测、大模型训练均不作为毕业设计必做承诺。

| [AutoSurvey，NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/hash/d07a9fc7da2e2ec0574c38d5f504d105-Abstract-Conference.html) 分阶段检索、拟定大纲、分节撰写并整合修订 | 保存章节计划，增加章节整合检查，并保留各步骤的依据 |

## 4. 两场景、三阶段的工作台

项目创建时选择 `undergraduate_thesis` 或 `intro_paper`，保存题目、研究问题、学校/投稿规范、研究材料、用户确认的事实、章节大纲和阶段进度。切换场景须预览差异，不清空已有稿件。

| 阶段 | 本科毕业论文 | 入门级学术小论文 | 必须保存的产物 |
|---|---|---|---|
| 写作准备 | 课题要求、学校规范、文献比较、章节职责与材料缺口 | 研究问题、目标体例、研究路线比较与精简论证计划 | 场景配置、阅读记录、比较候选、章节计划及版本、材料状态 |
| 内容撰写 | 围绕章节目标组织设计、实现和实际测试材料 | 按问题—方法—结果组织用户提供的研究材料 | 论断与依据、建议、用户选择、稿件版本、章节摘要 |
| 检查完善 | 检查目标—实现—测试—结论对应关系、术语、引用与学校规范 | 检查问题—方法—结果—结论对应关系、引用与目标体例 | 带定位的问题清单、检查覆盖范围、下一步、处理与复查状态 |

大纲不强制套用某个通用论文目录。用户已确认的课题要求与真实实验数据优先，材料缺失时输出待补项，不生成虚构实验。阶段可以回退和迭代，不能用聊天轮数代替阶段完成度。

规范资源库首版采用可维护的条目：适用场景、规范来源、版本/日期、规则内容、示例和适用章节。区分学校正式要求、通用写作建议与模型建议；未提供校方要求时不自称“符合学校全部规范”。

### 4.1 可编辑的组织产物

文献阅读记录保存研究问题、方法、对象、评价条件、结果和限制，各字段关联原文或明确标注未报告。文献比较记录本次问题、比较轴、分组、共性、差异、冲突与缺项；评价条件不同的结果不直接合并或排名。章节计划记录职责、拟回答的问题、候选论断、已有材料、缺项、顺序和章节依赖。章节摘要记录指定稿件版本实际表达的内容与术语，用于导航；事实核查仍回读正文及原始资料。

上述产物属于统一项目知识空间，允许列表、分组卡片或按需展开的矩阵视图；用户可以直接编辑已有正文，无需先填完表格。每次任务优先说明“如何组织、为何修改、还需补什么”，并给出少量可执行的下一步。系统可自动保存派生分析；AI 要替换用户已采用的章节计划时，先生成候选并请求确认。

## 5. 按任务选用检索与工具

统一请求上下文由服务端装配：项目配置 + 当前任务 + 稿件版本/选区 + 适用规范 + 有界历史 + 必要证据。前端传来的项目 ID、材料 ID、版本和选区均需校验归属与有效性。

| 任务 | 检索策略 | 输出边界 |
|---|---|---|
| 语句精简、语法或风格调整 | 默认不检索，只读取选区及必要上下文 | 不新增事实、数据和引用；存在歧义则提问 |
| 资料理解、文献综合、带事实的段落辅助 | 检索项目原始材料，筛选去重后生成 | 论断关联证据；无充分资料则列待补项 |
| 大纲与写作计划 | 先读取研究目标和规范，按需要检索资料 | 解释结构依据，要求用户确认 |
| 全文检查 | 读取大纲和章节，逐章检查后全局汇总；回读相关原文 | 输出问题位置、类型、理由、建议、依据及不确定性 |

首版先完成单次检索的可重复流程，再增加有必要的二次检索。Agent 可以用于复杂任务，但须有服务端工具白名单、超时、调用次数和 token 预算；“最多四轮”写在提示里不算硬限制。实际模型、提示版本、检索配置及降级情况写入运行记录，不能静默换模型后仍称为同一实验条件。

用户资料、检索片段、wiki 内容均视为数据，不因其中出现指令而改变工具权限。私有全文发送至外部模型前明确告知范围，优先只发送必要片段；不记录 API 密钥，不自动抓取或传播学校订阅全文。

### 5.1 典型任务契约

| 任务 | 必要输入 | 可组合的处理步骤 | 可见输出与边界 |
|---|---|---|---|
| 相关工作 | 研究问题、所选文献、比较轴或当前章节 | 提取带来源要素 → 比较与分组 → 形成章节计划 → 局部写作 → 回读证据 | 比较、计划、局部候选与缺项；保留未报告字段，不虚构共同评价条件 |
| 系统设计 | 目标与约束、用户设计选择、章节计划、说明或代码快照 | 对应目标与设计选择 → 梳理模块及数据流 → 关联材料 → 形成解释候选 | 设计论证、模块关系与待说明项；代码静态分析不能证明已运行或已通过测试 |
| 结果讨论 | 用户结果、环境、指标、基线、章节计划 | 对应目标与结果 → 核对比较条件 → 分析限制 → 形成局部候选 | 有依据的讨论及待补项；不补造数据、显著性或未开展的实验 |
| 全文检查 | 固定稿件快照、蓝图、章节计划、适用规范与资料 | 规则检查 + 局部分析 + 依赖章节回读 → 跨章节对应检查 → 汇总 | 问题及两端位置、理由、依据、下一步与覆盖范围；材料不足、未检查、失败和不适用分别显示 |

这些步骤供开放式 Planner 按意图选用，不是每次任务必须执行的固定流水线。局部润色可以直接处理选区；已有成熟正文可以直接检查。目标对应、术语变化或结论越界等问题必须回读相关正文，不能只依据章节摘要。

### 5.2 上下文与结果校验

按任务装配：场景、阶段和目标，选区及稿件快照，相关蓝图字段，章节计划，必要的比较记录，依赖章节摘要，原文片段，适用规范和输出要求。摘要与比较不能替代原始证据；若它们参与实验，两组输入须按实验目的控制一致。

任务结果按需包含组织产物、批注、候选修改、下一步、检查覆盖范围、证据引用与依赖记录。服务端验证项目归属、来源版本、引用 ID、文本锚点及结果结构；无材料时允许正常完成为“需要补充材料”，不能编造回答，也不能把该结果混同模型调用失败。

运行协调器负责超时、预算、取消、版本事务和持久化；模型只提出内容规划和分析。部分检查失败时保留已完成结果并列明未完成范围，不能显示为全篇检查通过。

## 6. 可核查的证据链

### 6.1 来源定位

拟将工具返回从“序号 + 文件名 + 文本”升级为结构化 `EvidenceRef`：

```text
evidence_id / project_id
source_id / source_version / chunk_id / index_generation
locator: page? / paragraph_id? / start? / end? / locator_kind
excerpt / retrieval_method / retrieval_score
```

`evidence_id` 与原始来源版本绑定，不能由模型任意创建。引用序号只用于显示，不能作为跨会话身份。服务端根据本次已授权证据集合校验引用，证据详情接口再次检查项目权限。

PDF 优先提取物理页序号，并标明与印刷页码的区别；坐标准确时才高亮。DOCX/TXT 使用段落或文本区间定位，不捏造 DOCX 的固定页码。提取失败、扫描件或无法定位时明确提示，提供文件与摘录回查，不显示虚假的精确位置。分块长度和重叠量属于待调参数，应记录实际计量单位，不能把字符数当作 token 数。

排序分数只表示检索排序，不代表事实可信度。引用支持状态可记录为未核验、自动提示待核验、人工已核验；人工核验状态也不等于系统保证论断绝对正确。模型自报“0.95 置信度”不作为真实可靠性指标。

资料处理状态与论断支持评估分别保存。`evidence_ready` 仅表示有可回查的片段和定位，不表示内容已验证。`SupportAssessment` 绑定特定论断版本及证据集合，记录支持、反驳、条件不同、未报告或无法判断，以及核查方式和时间；只有元数据时不能推断未读取的论文正文。

### 6.2 RRF 校正与测试

按原论文公式，拟对两个截断候选列表采用：`score(d) = Σ 1 / (60 + rank_i(d))`，名次从 1 开始。本项目约定未进入某路候选列表时该路贡献为 0，同一路重复片段只记一次；同分按稳定 ID 排序。

当前 `Store.Search` 将零起始名次相加后只取一次倒数；仅 BM25 命中的片段被加上固定 10000，丢失该路实际名次。因此不能把现有输出当作标准 RRF 实验结果。例：A 仅向量第 1，B 两路均第 2；标准融合应有 `score(B)=2/62 > score(A)=1/61`，当前实现却分别为 `1/63` 与 `1/61`。

优先补回归用例：双路共同命中、单路缺失、BM25 独有命中顺序、重复项、空查询/空库、嵌入失败降级、同分稳定性与跨项目隔离。该问题在本轮仅登记，尚未修改代码或运行修复后的测试。

> **已修复（2026-10-05，`agent-run-architecture` 期间）**：`Store.Search` 的融合改为按本文公式实现——名次**从 1 开始**，**逐路取倒数后相加**（`score(d) = Σ 1/(60 + rank_i(d))`），BM25 独有命中取该路**真实名次**（原先被加上固定 10000，分数塌到 ~1e-4 并被 top-k 截掉）。
> 回归用例：`internal/rag/rrf_test.go`（名次从 1 起、两路共同命中胜过单路第 1、分数不被基数压低）。
> **仍未做**：同分稳定性与稳定 ID 排序、空查询/空库、嵌入失败降级的显式用例；以及 §9.2 要求的 BM25 / 向量 / 融合三组对照实验。

### 6.3 索引与 wiki 的新鲜度

来源更新拟采用“建立新索引代次—校验—切换活动代次”，避免先删除旧片段再调用嵌入服务。新代次失败可重试，旧索引可以回查，但必须标注对应旧版材料；已删除或失去权限的来源立即停止用于生成。缓存键包含项目、代次与嵌入配置，不能只靠进程内清缓存保证一致性。

> **落地状态（2026-10-05，`data-integrity-refactor`）**：代次的**结构与状态流转已落地**——`rag_chunks.generation` + `rag_index_generations`（`building`/`active`/`superseded`/`failed`），写入侧优先落构建中的代次，检索侧四条路径（内存向量、BM25、库端向量下推、BM25 行取数）全部限定活动代次，代次切换为条件更新且切换后失效内存缓存。**仍未做**：把「来源变更 → 建新代次」接进真实的索引重建调度（当前由调用方显式 `BeginGeneration`/`ActivateGeneration`）；来源版本与撤权后失效（属 §8 证据身份）。

嵌入记录至少包含模型标识、维度、配置版本和来源内容摘要；更换模型必须重建对应向量。哈希嵌入等离线替身只验证流水线，不用于宣称语义检索质量。某路失败时记录实际运行模式，单独统计，不能混入完整混合检索成绩。

wiki 是派生笔记，不是新出现的一份原始证据。每个用于生成的笔记片段应能回溯到来源 ID、版本与证据 ID；原文变更、删除或撤权时标记受影响笔记过期。优先级应为“wiki 帮助导航—回读原始证据—形成建议”，不能“wiki 写过就当事实”；缺少溯源的现有笔记仅用于浏览，不作为已核验论据。

## 7. 修改确认与版本安全

拟采用以下状态流，禁止让普通聊天工具绕过确认直接修改用户稿件：

> **落地状态（2026-10-05，`agent-run-architecture`）**：确认流已落地。
> 主对话 agent **已摘除整文件覆盖的写盘工具**，改为 `propose_edit` 产出带锚点的建议；
> 建议记录产出时的稿件基准哈希，用户在面板上确认后由**服务端重新校验**归属、仍为待定、
> 以及基准哈希与当前内容一致，才执行替换（`server/internal/agent/proposals.go`）。
> 稿件变化后旧建议转 `stale`，不会用旧基准覆盖新内容；重复应用被拒。
>
> 会话入口：`POST /projects/:id/agent/conversations` 显式建会话（归属校验），
> 面板在**第一条消息**时先建会话再发 Run——此前没有任何建会话接口，
> 新项目的第一句话会静默丢失（e2e 抓到）。
>
> **仍未做**：不可变文件快照与版本回退、批注（WritingComment）与文本锚点区间、
> `deferred/needs_recheck` 的适用性生命周期、证据身份随来源撤权失效——这些仍属 §10 的 P0/P1 范围。

```text
任务执行：queued → running → completed / failed / cancelled
分析适用性：applicable / needs_recheck / stale（按依赖判定）
批注处理：open / deferred → resolved / rejected（适用性独立记录）
候选修改：pending → 用户确认 → 服务端校验版本 → applied
                    ↘ 用户拒绝 → rejected
                    ↘ 基础稿件变化 → stale（在当前版本重新生成并确认）
                    ↘ 执行失败 → failed（原稿仍可读取）
```

写作建议的主呈现形式是与文本锚定的批注：批注绑定项目、文件、基准版本、原文区间或文档级目标、问题类型/严重度、理由和证据集合。`ChangeProposal` 是批注可选附带的候选修改，而不是批注生成后的自动写入动作；前端在用户请求应用时才显示实际 diff，并支持拒绝、编辑后采用、手工修改后解决批注和分项处理。服务端应用时重新校验权限、基准版本与幂等键，不能只相信前端已展示过确认框。

采用不可变文件快照：先保存新对象，数据库事务中以版本条件更新当前指针和建议状态；冲突时返回失败，不覆盖用户期间的修改。未引用的新对象可后续清理。回退是创建一个恢复版本，不破坏历史。多文件修改只有全部校验及对象写入成功后才切换指针。

分析适用性按实际读取的文本范围、计划、蓝图字段、规范和来源版本判断，无关修改不让全部分析失效。全局审阅可依赖全文；无法确定影响面时保守复查。检索任务还记录查询、授权范围、索引代次与候选集合：“缺少依据”或“研究覆盖不足”等判断依赖搜索范围，相关新资料出现后需复查，不能仅因尚未读取就视为无关。来源撤权、删除或被排除后立即停止后续使用并标记受影响记录。

分析仍可参考不代表旧差异可以应用。基础稿件版本改变后，旧候选修改必须失效；在当前版本生成新候选、重新确认，并由服务端执行版本条件更新。普通资料准入、元数据、摘要和比较的自动保存遵循项目策略；对稿件、正式引用及蓝图正式目标、方法和事实的 AI 更新须用户确认。

应用前也重新核查所用证据的权限、准入和关键依赖，不能仅凭正文版本未变就应用。依赖已失效或待复查的候选先重查并形成新候选；旧确认不授权使用被删除、撤权或排除的来源。

编译是已保存版本上的独立运行：使用项目配置的编译器、固定输入版本及受限环境。编译失败保留此前可用稿件和新版本，显示日志供修订，不自动覆盖或丢弃用户改动。文件路径、项目权限、编译资源限制均由服务端控制。

## 8. 最小数据与接口增量

避免先搭建通用工作流平台。以下均为拟新增或调整的契约，最终字段在对应 OpenSpec 中确定：

| 数据对象 | 最少需要表达的内容 |
|---|---|
| ProjectWritingState | 场景、研究问题、课题要求与约束、计划、大纲、规范版本、进度及修订号 |
| WritingRun | 输入版本、任务/提示/模型配置、证据快照、运行状态、错误、耗时及用量 |
| WritingComment / ChangeProposal / DocumentRevision | 批注的快照与文本锚点（或文档级目标）、类别、理由、证据、处理状态；候选差异、确认人、幂等键、新旧对象引用 |
| NormEntry | 适用范围、规则、来源、版本及示例 |
| 现有 RAG/wiki 增量 | 来源版本、索引代次、定位信息、笔记依赖及过期状态 |
| LiteratureNote / LiteratureComparison | 带证据的文献要素、比较问题与轴、分组、条件差异、缺项及派生版本 |
| ChapterPlan / ChapterDigest | 章节职责、候选论断、材料与依赖；指定稿件版本的摘要和术语；用户采用状态 |
| SupportAssessment / RunDependency | 论断与证据的支持关系和核查方式；实际文本、来源、规范、检索范围与版本依赖 |

先复用项目与文档表，仅在需要独立查询、约束和审计时拆表。会话历史不是研究事实和当前稿件的唯一存储。

接口职责拟分为：项目写作状态读写、阅读与比较结果查询及编辑、章节计划编辑与候选采用、章节摘要更新、启动/查询/取消运行、查看证据及支持评估、查询/解决/拒绝/追问批注、查看/接受/拒绝候选修改、查询/恢复稿件版本、读取规范条目。沿用项目级路径与鉴权约定，不在本文件中把拟议路由冒充现有 API。

现有流式事件应兼容其 `meta`、文本及工具事件，增量加入 `run_id` 和事件序号。首版至少可在刷新后查询持久化终态与结果；重连不自动重复运行写操作。断流不等于成功，取消也不等于已撤销生效的修改，界面分别展示运行状态和稿件状态。

## 9. 验证与验收

### 9.1 功能、性能与可用性

| 验证范围 | 必须留下的证据 |
|---|---|
| 两场景 × 三阶段 | 固定案例、操作步骤、输入输出、截图及成功/失败记录；不能只演示聊天 |
| 修改保护 | 拒绝不写入、旧版本冲突、重复提交幂等、版本恢复、多文件失败与编译失败测试 |
| 引用与资料 | 引用 ID 合法性、项目隔离、原文支持情况、定位失败、资料不足、更新/删除后失效测试 |
| 持久化与异常 | 重启/重新登录后稿件与进度保留；模型超时、限流、断流及取消后状态一致 |
| 全文检查 | 固定植入结构、衔接、术语与引用问题的稿件，记录定位与误报；区分规则校验和模型建议 |
| 组织产物与章节协同 | 阅读字段的证据与缺项；不同条件的比较；编辑分类和计划后重新组织；目标—实现—测试—结论关联、两端定位与未完成检查 |
| 依赖与自动保存 | 普通入库无需逐条确认、派生分析不晋升正式事实；无关编辑保留分析、相关变化复查、检索范围变化复查负向判断、旧候选不得写回 |
| 可用性 | 以开发者自测为主，按固定任务完成查依据、处理批注、采纳/拒绝候选修改和恢复版本，记录过程、耗时和问题；不以邀请外部用户为前提，也不外推长期学习效果 |

课题验收目标为核心功能测试通过率 ≥90%。测试前固定核心用例集合，报告通过/失败/未执行数量；未执行不能算通过。用例通过率不是代码覆盖率，关键写作主流程和权限/数据安全缺陷不能用其他用例的高分抵消。

课题性能目标为除大模型内容生成外主要操作 ≤3 秒。预先列出项目打开、列表加载、稿件保存、进度更新等操作、测试环境、数据规模、并发量和计时边界，逐项记录最大值及超时次数，P50/P95 仅作补充。不能以请求入队耗时冒充编译、解析或索引完成耗时；长任务分别报告提交与最终完成时间，是否属豁免范围需在验收前说明，不能自行扩大“大模型生成”的例外。

### 9.2 与开题报告一致的小规模实验

**提示评价基线为约 30 个固定写作任务，与正式报告 3.4 一致，另设独立开发任务。** 覆盖两种场景和准备、撰写、检查三个阶段，纳入有材料、材料不足和已有正文修改的情况；具体数量、分配、合法材料、期望输出和评分准则在实施前冻结。开发任务用于调提示，评价任务不能反复用于调参；本轮不预设实验结果。

| 评价层次 | 比较方式与控制条件 | 记录什么 |
|---|---|---|
| 提示评价，必做 | 同一模型、采样参数、输出上限、材料、原文片段，比较通用提示与场景/阶段提示；使用比较记录或章节计划时两组提供相同产物 | 任务完成、要求遵循、组织合理性、可操作性、原意与事实保持、引用支持、时延及用量 |
| 检索评价 | 从资料任务中选取有预标注依据的查询，比较 BM25、向量与校正后的融合；语料、查询和 top-k 相同，降级结果单列 | Hit@5 仅以有依据查询为分母；无依据案例单独记录补材料提示、错误作答与实际检索模式 |
| 流程探索，单列 | 按资源情况选固定任务中的综合/组织子集，比较直接生成与提取—组织—生成—检查；模型和原始材料相同，新增组织上下文及调用次数明确记录 | 要素准确性、比较条件、章节职责覆盖、错误、完整流程耗时和用量；归因需考虑上下文与计算量变化 |

流程探索的任务数量和是否开展在实施前确定，结果单列；流程增加的上下文、工具调用和计算量不能归因于提示优化。

系统功能用例、提示评价任务和检索查询分别编号与统计，不能混算通过率。跨章节检查使用人工植入的目标遗漏、术语冲突、结果与结论不符等案例，记录两端定位、误报和覆盖范围；材料不足需正确指出下一步。随机化展示顺序并保存输入、配置、输出和评分记录；以开发者自评为主，模型评分仅作辅助，如实报告单人、小样本局限，不推断学生学习效果。真实结果若未改善，应分析失败条件，不删掉反例。

## 10. 实施顺序与答辩表达

1. **P0：安全与正确性前置。** 校正融合、补证据身份与版本、切断未经确认的稿件覆盖；完成回归测试。随后再对接真实 AI 面板，避免将现有直接写工具直接暴露为可用功能。
2. **P1：完整写作流程。** 先以本科论文场景打通材料阅读与比较—可编辑章节计划—带证据建议—用户采纳—保存与编译—章节整合检查，再覆盖小论文场景与规范条目；用户可从已有正文直接进入局部任务。
3. **P1：持久化和失败恢复。** 运行记录、索引代次、wiki 失效、稿件恢复和状态一致性；完成中期演示。
4. **验收：必做测试与评价。** 完成功能、性能、开发者走查和约 30 个固定任务的提示对照，保留失败证据与部署记录。重排模型、复杂 OCR 等可选增强在核心交付完成后考虑；它们不替代必做测试。

具体月份见 [开发路线图](11-roadmap.md)。实现涉及新表、接口或跨模块行为时按 [OpenSpec 流程](../agents/openspec-workflow.md) 单独建立变更；不修改 archive，不因代码存在就勾选已验收。

答辩可说明的工程特色是“将材料转化为比较与章节论证计划、围绕章节目标提供有依据的写作辅助、用户控制修改、跨章节检查与分层验证”。不宣称发明 RAG/RRF，不以“多 Agent”数量代替工作量，不以演示成功代替全部测试。
