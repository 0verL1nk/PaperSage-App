# 调研驱动的 AI 写作实现方案

更新：2026-09-16。状态：**后续实施基线，不是已实现或已通过测试的声明**。本轮仅调整文档，不修改业务代码、数据库或既有 OpenSpec 完成状态。

## 1. 定位与范围

正式课题为“基于大模型的科研论文写作AI辅助系统设计与实现”，面向中国大陆本科生及科研入门者。以任务书的两类场景、三阶段流程、四个业务模块为主线，研究重点是系统设计、提示优化和测试，不是训练基础模型或提出新的检索算法。

保留现有 React/TypeScript 前端和 Go/Gin 后端，沿用现有编辑、存储与编译能力。前后端分离指交互与服务职责分离，不要求为了答辩拆成许多微服务。暂不新增 Python 解析服务、Elasticsearch、独立向量数据库等必需依赖；部署数据库及向量扩展的兼容性由实际迁移和集成测试确定，不因存在适配分支就宣称全部支持。

必做：用户管理、分场景写作工作台、全流程 AI 辅助、学术规范资源库；持久化、来源核查、用户确认、部署演示和三类测试。复杂 OCR、跨项目知识图谱、实时多人协作、自动投稿、Word 双向编辑、查重/AI 检测、大模型训练均不作为毕业设计必做承诺。

## 3. 文献如何影响设计

本节区分研究观察与本项目的工程推导；详细阅读边界见 [文献记录](../proposal/交付/文献来源与阅读边界.md)。文献的结果不直接证明本系统有效。

| 文献依据 | 本项目据此采取的设计选择 |
|---|---|
| [Lin：学术写作中的生成式 AI](https://www.nature.com/articles/s41551-024-01185-8) 讨论阶段、反馈和作者选择；属于观点性框架 | 按准备、撰写、检查组织任务；默认产出建议，不替作者决定研究内容 |

| [CoEdIT](https://aclanthology.org/2023.findings-emnlp.350/) 研究任务指令微调，[STORM](https://aclanthology.org/2024.naacl-long.347/) 研究百科类写作前的资料组织 | 明确修改目标、先组织依据再拟大纲；不复现训练或开放式全网写作系统 |

| [RRF 原论文](https://cormack.uwaterloo.ca/cormack/cormacksigir09-rrf.pdf) 给出按各路名次分别取倒数再求和的融合方式 | 先保证检索实现与公式一致，再开展消融实验；不预设混合检索一定最好 |

## 4. 两场景、三阶段的工作台

项目创建时选择 `undergraduate_thesis` 或 `intro_paper`，保存题目、研究问题、学校/投稿规范、研究材料、用户确认的事实、章节大纲和阶段进度。切换场景须预览差异，不清空已有稿件。

| 阶段 | 本科毕业论文 | 入门级学术小论文 | 必须保存的产物 |
|---|---|---|---|
| 写作准备 | 任务书约束、写作计划、学校规范、章节大纲 | 研究问题、目标体例、资料边界、精简大纲 | 场景配置、计划、大纲版本、材料状态 |
| 内容撰写 | 按章节辅助组织系统设计、实现和实际测试材料 | 按问题—方法—结果组织用户提供的研究材料 | 建议、理由、证据、用户选择及稿件版本 |
| 检查完善 | 全文结构、章节衔接、术语、引用与学校规范 | 论证连贯性、术语、引用与目标体例 | 带定位的问题清单、处理状态、复查结果 |

大纲不强制套用某个通用论文目录。用户已确认的任务书与真实实验数据优先，材料缺失时输出待补项，不生成虚构实验。阶段可以回退和迭代，不能用聊天轮数代替阶段完成度。

规范资源库首版采用可维护的条目：适用场景、规范来源、版本/日期、规则内容、示例和适用章节。区分学校正式要求、通用写作建议与模型建议；未提供校方要求时不自称“符合学校全部规范”。

## 5. 按任务选用检索与工具

统一请求上下文由服务端装配：项目配置 + 当前任务 + 稿件版本/选区 + 适用规范 + 有界历史 + 必要证据。前端传来的项目 ID、材料 ID、版本和选区均需校验归属与有效性。

| 任务 | 检索策略 | 输出边界 |
|---|---|---|
| 语句精简、语法或风格调整 | 默认不检索，只读取选区及必要上下文 | 不新增事实、数据和引用；存在歧义则提问 |
| 资料理解、文献综合、带事实的段落辅助 | 检索项目原始材料，筛选去重后生成 | 论断关联证据；无充分资料则列待补项 |
| 大纲与写作计划 | 先读取研究目标和规范，按需要检索资料 | 解释结构依据，要求用户确认 |
| 全文检查 | 读取大纲和章节，逐章检查后全局汇总；回读相关原文 | 输出问题位置、类型、理由、建议、依据及不确定性 |

首版先完成单次检索的可重复流程，再增加有必要的二次检索。Agent 可以用于复杂任务，但须有服务端工具白名单、超时、调用次数和 token 预算；“最多四轮”写在提示里不算硬限制。实际模型、提示版本、检索配置及降级情况写入运行记录，不能静默换模型后仍称为同一实验条件。

用户资料、检索片段、wiki 内容均视为数据，不因其中出现指令而改变工具权限。私有全文发送至外部模型前明确告知范围，优先只发送必要片段；不记录 API 密钥，不自动抓取或传播学校订阅全文。

## 6. 可核查的证据链

### 6.1 来源定位

拟将工具返回从“序号 + 文件名 + 文本”升级为结构化 `EvidenceRef`：

```text
evidence_id / project_id
source_id / source_version / chunk_id / index_generation
locator: page? / paragraph_id? / start? / end? / locator_kind
excerpt / retrieval_method / retrieval_score
```

`evidence_id` 与原始来源版本绑定，不能由模型任意创建。引用序号只用于显示，不能作为跨会话身份。服务端根据本次已授权证据集合校验引用，证据详情接口再次检查项目权限。

PDF 优先提取物理页序号，并标明与印刷页码的区别；坐标准确时才高亮。DOCX/TXT 使用段落或文本区间定位，不捏造 DOCX 的固定页码。提取失败、扫描件或无法定位时明确提示，提供文件与摘录回查，不显示虚假的精确位置。分块长度和重叠量属于待调参数，应记录实际计量单位，不能把字符数当作 token 数。

排序分数只表示检索排序，不代表事实可信度。引用支持状态可记录为未核验、自动提示待核验、人工已核验；人工核验状态也不等于系统保证论断绝对正确。模型自报“0.95 置信度”不作为真实可靠性指标。

### 6.2 RRF 校正与测试

按原论文公式，拟对两个截断候选列表采用：`score(d) = Σ 1 / (60 + rank_i(d))`，名次从 1 开始。本项目约定未进入某路候选列表时该路贡献为 0，同一路重复片段只记一次；同分按稳定 ID 排序。

当前 `Store.Search` 将零起始名次相加后只取一次倒数；仅 BM25 命中的片段被加上固定 10000，丢失该路实际名次。因此不能把现有输出当作标准 RRF 实验结果。例：A 仅向量第 1，B 两路均第 2；标准融合应有 `score(B)=2/62 > score(A)=1/61`，当前实现却分别为 `1/63` 与 `1/61`。

优先补回归用例：双路共同命中、单路缺失、BM25 独有命中顺序、重复项、空查询/空库、嵌入失败降级、同分稳定性与跨项目隔离。该问题在本轮仅登记，尚未修改代码或运行修复后的测试。

### 6.3 索引与 wiki 的新鲜度

来源更新拟采用“建立新索引代次—校验—切换活动代次”，避免先删除旧片段再调用嵌入服务。新代次失败可重试，旧索引可以回查，但必须标注对应旧版材料；已删除或失去权限的来源立即停止用于生成。缓存键包含项目、代次与嵌入配置，不能只靠进程内清缓存保证一致性。

嵌入记录至少包含模型标识、维度、配置版本和来源内容摘要；更换模型必须重建对应向量。哈希嵌入等离线替身只验证流水线，不用于宣称语义检索质量。某路失败时记录实际运行模式，单独统计，不能混入完整混合检索成绩。

wiki 是派生笔记，不是新出现的一份原始证据。每个用于生成的笔记片段应能回溯到来源 ID、版本与证据 ID；原文变更、删除或撤权时标记受影响笔记过期。优先级应为“wiki 帮助导航—回读原始证据—形成建议”，不能“wiki 写过就当事实”；缺少溯源的现有笔记仅用于浏览，不作为已核验论据。

## 7. 修改确认与版本安全

拟采用以下状态流，禁止让普通聊天工具绕过确认直接修改用户稿件：

```text
生成建议 → pending → 用户确认 → 服务端校验版本 → applied
                  ↘ 用户拒绝 → rejected
                  ↘ 原稿变化 → stale（重新生成差异并确认）
                  ↘ 执行失败 → failed（原稿仍可读取）
```

建议绑定项目、文件、基准版本、原文区间、建议内容、修改理由和证据集合；前端显示实际 diff，并支持拒绝、编辑后采用与分项处理。服务端应用时重新校验权限、基准版本与幂等键，不能只相信前端已展示过确认框。

采用不可变文件快照：先保存新对象，数据库事务中以版本条件更新当前指针和建议状态；冲突时返回失败，不覆盖用户期间的修改。未引用的新对象可后续清理。回退是创建一个恢复版本，不破坏历史。多文件修改只有全部校验及对象写入成功后才切换指针。

编译是已保存版本上的独立运行：使用项目配置的编译器、固定输入版本及受限环境。编译失败保留此前可用稿件和新版本，显示日志供修订，不自动覆盖或丢弃用户改动。文件路径、项目权限、编译资源限制均由服务端控制。

## 8. 最小数据与接口增量

避免先搭建通用工作流平台。以下均为拟新增或调整的契约，最终字段在对应 OpenSpec 中确定：

| 数据对象 | 最少需要表达的内容 |
|---|---|
| ProjectWritingState | 场景、研究问题、任务书约束、计划、大纲、规范版本、进度及修订号 |
| WritingRun | 输入版本、任务/提示/模型配置、证据快照、运行状态、错误、耗时及用量 |
| ChangeProposal / DocumentRevision | 基准版本、实际差异、确认人、状态、幂等键、新旧对象引用 |
| NormEntry | 适用范围、规则、来源、版本及示例 |
| 现有 RAG/wiki 增量 | 来源版本、索引代次、定位信息、笔记依赖及过期状态 |

先复用项目与文档表，仅在需要独立查询、约束和审计时拆表。会话历史不是研究事实和当前稿件的唯一存储。

接口职责拟分为：项目写作状态读写、启动/查询/取消运行、查看证据、查看/接受/拒绝修改建议、查询/恢复稿件版本、读取规范条目。沿用项目级路径与鉴权约定，不在本文件中把拟议路由冒充现有 API。

现有流式事件应兼容其 `meta`、文本及工具事件，增量加入 `run_id` 和事件序号。首版至少可在刷新后查询持久化终态与结果；重连不自动重复运行写操作。断流不等于成功，取消也不等于已撤销生效的修改，界面分别展示运行状态和稿件状态。

## 9. 验证与验收

### 9.1 功能、性能与可用性

| 验证范围 | 必须留下的证据 |
|---|---|
| 两场景 × 三阶段 | 固定案例、操作步骤、输入输出、截图及成功/失败记录；不能只演示聊天 |
| 修改保护 | 拒绝不写入、旧版本冲突、重复提交幂等、版本恢复、多文件失败与编译失败测试 |
| 引用与资料 | 引用 ID 合法性、项目隔离、原文支持情况、定位失败、资料不足、更新/删除后失效测试 |
| 持久化与异常 | 重启/重新登录后稿件与进度保留；模型超时、限流、断流及取消后状态一致 |
| 全文检查 | 固定植入结构、衔接、术语与引用问题的稿件，记录定位与误报；区分规则校验和模型建议 |
| 可用性 | 让试用者完成查依据、采纳/拒绝修改、恢复版本等任务，记录完成情况、耗时和意见；不外推长期学习效果 |

任务书规定核心功能测试通过率 ≥90%。测试前固定核心用例集合，报告通过/失败/未执行数量；未执行不能算通过。用例通过率不是代码覆盖率，关键写作主流程和权限/数据安全缺陷不能用其他用例的高分抵消。

任务书要求除大模型内容生成外主要操作 ≤3 秒。预先列出项目打开、列表加载、稿件保存、进度更新等操作、测试环境、数据规模、并发量和计时边界，逐项记录最大值及超时次数，P50/P95 仅作补充。不能以请求入队耗时冒充编译、解析或索引完成耗时；长任务分别报告提交与最终完成时间，是否属豁免范围需在验收前说明，不能自行扩大“大模型生成”的例外。

### 9.2 与开题报告一致的小规模实验

拟采用两个计算机主题、约 30 篇可合法测试的资料、20 个开发任务与 40 个固定测试任务。测试集为 20 个有依据的理解问答、10 个资料综合任务及 10 个资料不足任务；人工预先标注依据和作答条件。开发集调整参数后冻结测试集，不能反复按测试结果调提示。

检索比较 BM25、向量、校正后的混合检索；使用相同语料、查询和 top-k。Hit@5 的分母只含有标注依据的任务，资料不足任务单独评估是否正确提示补充信息。生成比较：通用提示无资料、通用提示加检索、场景提示加相同检索；后两组证据列表保持一致，固定模型、采样参数与输出上限。

分别记录任务完成、来源存在、论断支持、必要引用覆盖、修改可采纳性和时延/用量。随机化展示顺序，保存评分准则；模型评分仅作辅助，单人评价及小样本局限如实报告。真实结果若未改善，应分析失败条件，不删掉反例。

## 10. 实施顺序与答辩表达

1. **P0：安全与正确性前置。** 校正融合、补证据身份与版本、切断未经确认的稿件覆盖；完成回归测试。随后再对接真实 AI 面板，避免将现有直接写工具直接暴露为可用功能。
2. **P1：一个完整纵向流程。** 先以本科论文场景打通准备—带证据建议—用户采纳—保存—编译—检查，再补小论文场景与规范条目。
3. **P1：持久化和失败恢复。** 运行记录、索引代次、wiki 失效、稿件恢复和状态一致性；完成中期演示。
4. **P2：测试和可选增强。** 固定实验、可用性反馈及部署稳定性优先；重排模型、复杂 OCR、自动 wiki 整理只在核心验收完成后考虑。
