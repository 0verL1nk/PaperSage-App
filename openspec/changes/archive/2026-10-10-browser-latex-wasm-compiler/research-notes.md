## Findings

1. **Browser execution is real.** SwiftLaTeX runs compilation in WebAssembly workers, so the browser can own the actual engine invocation without sending TeX source to the compile server.
2. **Engine coverage is not the full PaperSage selector set yet.** The inspected SwiftLaTeX baseline contains pdfTeX and XeTeX. This review did not establish a usable LuaTeX WASM implementation; LuaTeX needs its own feasibility/build spike.
3. **XeLaTeX output needs a finalizer.** XeTeX emits XDV. A browser compile flow must run a compatible xdvipdfmx WASM stage before treating output as a PDF artifact.
4. **One engine run is one pass.** The front end must own reruns and auxiliary tools such as bibliography/index generation. The engine adapter should expose a single pass and structured outputs.
5. **Package UX and durable cache require added work.** Existing resource fetching is not sufficient for visible byte progress and persistent cache reuse. Add a resource manager with versioned manifests and explicit cache lifecycle events.
6. **Backend still owns durable state.** The browser can compile, but it should submit results to Go. Go authenticates/authorizes, uploads to Cloudflare R2 (S3-compatible), and updates the database job state.
7. **Refreshed XeTeX is a port, not a version bump.** A private SwiftLaTeX mirror is available at [papersage-swiftlatex](https://github.com/0verL1nk/papersage-swiftlatex), with upstream synchronization configured. Current TeX Live WEB sources were regenerated for XeTeX 0.999998 and successfully linked with Emscripten 3.1.64. The generated-core WASM build succeeded; browser runtime, XDV finalization, and the older C++ font/shaping dependencies still need smoke/compatibility verification.
8. **Current pdfTeX refresh links successfully.** TeX Live's current pdfTeX WEB core is 1.40.29 and the SwiftLaTeX WASM target links with Emscripten 3.1.64. The `zlib-fmt.ch` change is excluded because the current WASM filesystem shim has no gzip-format-file support. Runtime use still depends on supplying a format and TeX Live resources.
9. **PaperSage UI is still CLSI-only.** `WritingPage` submits to the existing asynchronous CLSI queue and obtains output by `build_id`. Browser compilation requires a distinct persisted-job creation/completion path, a dedicated worker adapter, local preview, then authenticated artifact publication through the existing Go/R2 boundary.
10. **The default SwiftLaTeX package/format endpoint is unavailable in the current environment.** A real browser-worker smoke run of pdfTeX 1.40.29 failed before TeX execution because `/pdftex/10/swiftlatexpdftex.fmt` could not be fetched; direct DNS/HTTP checks also failed for the documented legacy hosts. Do not ship the stock endpoint as the resource strategy.
11. **A dynamic package service is not required by the browser engine.** The user prefers an explicit setup page that downloads and caches engine resources locally. The planned path is browser-side format generation, a public TeX Live package index/source, browser-side package extraction, and IndexedDB cache; a static R2 mirror is only a fallback if public-source CORS/redirect behavior fails. [TeXFlow's architecture](https://github.com/ahnafia/texflow) is a useful implementation reference for TeX Live filename lookup and local format caching, but its server deployment is not a PaperSage requirement.
12. **Public-source browser access is not yet verified.** A Chromium fetch probe to two CTAN endpoints failed in this environment, and direct curl to one mirror timed out; this does not distinguish CORS from network reachability. Validate from the actual supported deployment origin before committing to a source or fallback.
13. **Downloads must survive leaving the page.** The user requires resumable initialization. Large engine/package resources must persist partial byte ranges in IndexedDB and resume with HTTP `Range` plus a stable resource validator/version; a source that cannot satisfy CORS and Range requirements cannot be used for large downloads.
14. **Resumable engine asset flow is implemented and browser-verified locally.** The WritingPage initialization dialog downloads pinned pdfTeX/XeTeX/Dvipdfmx JS/WASM assets into IndexedDB in 1 MiB HTTP ranges; each complete range and progress record is committed before advancing. A Chromium smoke interrupted after 1 MiB, reloaded, resumed at `bytes=1048576-1796922`, validated the complete SHA-256, then confirmed the service worker served the cached WASM with `application/wasm`. Vite static delivery returned `206` and valid `Content-Range` for both initial and `If-Range` requests. Vite emits weak ETags, so `If-Range` uses Last-Modified; the final content hash remains the integrity check. An interrupted in-flight 1 MiB segment is retried, while earlier committed ranges are retained. This validates the local same-origin asset path, not yet a deployed Vercel/R2 origin or package/font downloads.
15. **The current editor has no TeX source formatter or static diagnostic provider.** `frontend/src/lib/monaco-latex-lsp.ts` registers syntax highlighting, document outline, and completion only. The current Lezer parser is used for outline extraction but parser errors are not published as editor markers. `latex_render`'s TinyTeX image installs selected packages but does not wire a formatter/linter into WritingPage; the production full TeX Live image is not part of the target browser path. Source formatting (for example, indentation/layout) and static lint diagnostics (for example, unmatched environments or undefined references) are separate capabilities from compile-time errors and need an explicit browser-side decision.
16. **The target compile architecture is browser-only.** By user direction, `latex_render` is not a future compile dependency or fallback. The Go service remains responsible for authorized job state and publishing completed artifacts to object storage.
17. **A maintained alternative was tested rather than assumed compatible.** `corca-ai/wasmtex` was checked at commit `cd1a9a9` (2026-10-07). Its TeX Live 2025 engine manifest was release-cleared and all 37 assets passed the project's size/SHA-256 sync checks (27.7 MB across all engines; the XeTeX/converter subset is 8.4 MB). The browser log reports XeTeX `0.999997`; this is older than the PaperSage fork's refreshed XeTeX `0.999998`.
18. **WasmTex is not a drop-in success for the acceptance template.** In Chromium, it loaded the actual 31-file HIT ZIP and reached a 17-page, 169,168-byte XDV. The modern `xdvipdfmx` stage then reported `No image converter available` for `figures/golfer.eps` and emitted no PDF. Its own worker requires an EPS-to-PDF/PS converter for this case; the repository's compiler assets did not include one at that point. Browser-side EPS conversion is verified below.
19. **The template and resource mirror also need separate compatibility work.** The ZIP references `body/preface.tex` and `body/name.tex`, which are absent from the archive, and calls `\makecover` without a definition in its included `.cls`/`.sty`/`.cfg` files. The 2025 browser run also reported undefined `\tbl_save_outer_table_cols:` while processing tables. These are independent of the EPS converter and must remain visible as source/package diagnostics rather than being mislabeled as a WASM failure.
20. **The maintained project's default package mirror is not directly browser-readable from the tested PaperSage origin.** Chromium requests to `texlive.corca.ai` failed with `net::ERR_FAILED`/CORS while direct HTTP checks succeeded. A same-origin test proxy made package and font downloads work. Production therefore needs a CORS-configured Cloudflare R2 mirror or same-origin static proxy; the current test does not justify using the default cross-origin URL as-is.
21. **Cold resource loading is substantial and not yet interruption-safe across failed compiles.** The first XeTeX run emitted 389 package/font load events and exceeded the five-minute browser wait window before returning. WasmTex's docs say its persistent TeX Live cache is saved after a successful compile; after the failed EPS compile, the next run fetched the same early resources again. Its progress event reports files loaded but no fixed total. This does not satisfy the requested resumable, user-visible initialization on its own.
22. **Decision from the comparison.** Keep the refreshed private SwiftLaTeX XeTeX source as the engine baseline instead of swapping in WasmTex wholesale. The alternative is a useful reference for a modern XeTeX/dvipdfmx pipeline and TeX Live resource tracking, but it does not solve EPS, cross-origin delivery, template omissions, or failed-run cache persistence, and its XeTeX core is older. Continue the Swift fork path only with a browser-side EPS conversion stage and an independently verified XDV/PDF converter; retain the exact-source template errors in the compile UI.
23. **A Ghostscript browser build was evaluated, then not selected.** In Chromium, `@wasm-zoo/ghostscript@0.7.2` converted all six EPS files from the exact HIT archive into PDFs. The final implementation instead uses EtterScript; this avoids adding Ghostscript as another component while the existing SwiftLaTeX core's AGPL licensing is accepted.
24. **EPS preprocessing removes the first finalization blocker but does not produce an accepted PDF yet.** A second Chromium run converted all six EPS files in-browser, fetched 446 TeX Live resource events, and produced a 17-page, 236,960-byte XDV. The PDF finalizer still failed with `xdvipdfmx:fatal: Can't proceed...` after warning `Object @page.I already defined`; no PDF bytes were returned. The compile also surfaced the template's undefined commands/table errors and citation warnings. This run proves the converter stage can feed the browser XeTeX pipeline, not that either engine path passes acceptance.

25. **Root cause of the SwiftLaTeX package failure is the resource-resolution contract, not worker startup, CORS, or cache.** SwiftLaTeX calls Kpathsea synchronously with `(engine, format number, requested basename)` and expects the resource endpoint to return bytes plus a stable resource identifier. A flat static URL mirror works only when it contains the exact resolved resource under the exact format/name key. The real Chromium run fetched and cached dozens of base resources, then failed XeTeX format generation: the mirror returned 404 for `load-unicode-data`; a controlled `.tex` probe then exposed another 404 for `l3bitset.sty`. This proves extension guessing is neither complete nor safe, and the tested mirror inventory is incomplete for this worker format.
26. **Chosen root-level resource strategy.** Keep SwiftLaTeX compilation in the browser, but generate an immutable lookup catalog from the exact pinned TeX Live inventory with Kpathsea-compatible search semantics. The lookup key includes engine, numeric format, and requested filename; its value names the canonical TeX Live path, package provenance, and content hash. XeTeX Fontconfig family lookups need their own exact variant/name mapping. Publish the catalog and licensed resource objects to Cloudflare R2. A same-origin, read-only endpoint uses that catalog to return bytes and the `fileid`/`fontid` header expected by SwiftLaTeX. It does not run TeX or compile projects. The browser caches verified bytes by catalog revision and object identity. No extension guessing, filename-specific branches, or silent fallback to CLSI.

The browser adapter preserves the worker's original engine/format/name tuple; cached entries retain the original response ID and catalog revision. The Vite dev proxy targets the Go resolver. The catalog generator, complete TeX Live 2026 inventory, R2 publication, and real browser compile are still missing; the configured default profile will return a clear unavailable error until its catalog exists.

## Derived TeX runtime resource model (not yet profile-qualified)

- The catalog generator previously accepted only files inside `texmf-dist` with a TLPDB package archive record. That correctly rejects `texmf-var` generated files but leaves installation-generated runtime configuration such as Dvipdfmx's map outputs unresolvable. Treating those outputs as ordinary package members or concatenating every package `.map` file would not preserve the pinned TeX Live generation result.
- Schema 3 now has an optional `derived_resources` collection. Each exact lookup is bound to the generated artifact's SHA-256, size, media type and content-addressed object key; generator identity/version and executable SHA-256; and an input list containing input file SHA-256 plus TeX Live package revision, archive checksum, and license provenance. The Python generator validates and copies artifacts into `derived/<sha256>`. The catalog publisher validates/uploads only these generated artifacts before publishing the immutable catalog; ordinary package files remain on-demand. The Go resolver serves only exact catalog lookups, derives the storage key from the validated profile and content hash, and checks both size and SHA-256 before returning bytes.
- The manifest format is documented in `scripts/latex_resources/README.md`. It records declared generator inputs; the generator verifies these files and their package provenance but cannot independently prove the generator read-set is complete. A profile build must capture the complete input closure from the pinned generator invocation.
- This repository environment does not have the pinned TeX Live 2026 executable/tree needed to run `updmap-sys`; its `E:\texlive\2025` tree is only an empty skeleton, and the available MiKTeX 25.12 installation is not an interchangeable TeX Live build. No derived manifest was generated, no production catalog/object was written, and no CJK browser compile was accepted. The current profile therefore still lacks its generated map until a pinned build environment emits and qualifies the manifest.
- XeTeX font alias indexing also had a separate lookup mismatch: the generator discovered filename/PostScript/family aliases but did not emit the `font/OT|TT/<alias>` lookup used by the browser Fontconfig adapter. New catalog generation emits those exact alias tuples as well as the numeric-format XeTeX/Dvipdfmx entries. This code change does not alter the already-published immutable profile; a newly generated profile and browser CJK acceptance are still required.

## Browser bibliography toolchain research (2026-10-09)

- The current SwiftLaTeX adapter writes project files into the TeX worker and runs two bounded TeX passes, but it cannot read `.aux`/`.bcf` from the virtual filesystem or schedule an auxiliary bibliography engine. Bibliographies are therefore not supported by the current product flow even though the TeX engine itself can emit citation requests.
- Standard BibTeX integration needs a generic filesystem read/write contract: collect the root and nested `.aux` files, pass each bibliography request plus the project `.bib` and `.bst` files to BibTeX, write generated `.bbl` files back to the TeX worker, and rerun TeX with a bounded convergence policy. Missing inputs and unresolved citations must remain visible in the final diagnostics.
- [WasmTex's BibTeX worker](https://github.com/corca-ai/wasmtex/blob/main/wasm-build/bibtex-worker.js) and [controller](https://github.com/corca-ai/wasmtex/blob/main/src/engine/bibtex-engine.ts) are a practical browser reference: they use a separate Emscripten worker, MEMFS, Kpathsea format 6 (`.bib`) and format 7 (`.bst`) resolution, and explicit output reads. Reuse requires pinning and auditing its exact source revision and notices.
- BibTeX and Biber are distinct tools. BibTeX consumes `.aux` and produces `.bbl`; Biber consumes BibLaTeX's `.bcf` and produces Biber-format `.bbl`, so BibTeX cannot stand in for Biber. [TeX Live's BibTeX source](https://github.com/TeX-Live/texlive-source/blob/trunk/texk/web2c/bibtex.web) carries its own notices; [Biber](https://github.com/plk/biber) is Artistic-2.0. A [TeXlyre WASM build](https://github.com/TeXlyre/texlyre-busytex-build/tree/main/biber) demonstrates that Biber can be packaged with a Perl runtime, but adds a substantially larger runtime and its wrapper/build licensing needs separate review.
- Task 2.7 remains open. The next acceptance gate is a pinned browser BibTeX worker with a native TeX Live parity fixture covering `.aux` → BibTeX → `.bbl` → TeX, custom `.bst`, nested `\@input`, UTF-8/`@string`/`crossref`, missing files, cancellation, and bounded reruns. Biber needs a separate implementation and acceptance gate.
